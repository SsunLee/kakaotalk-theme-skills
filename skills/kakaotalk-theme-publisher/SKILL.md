# 카카오톡 테마 등록

사용자의 완성 테마와 플랫폼별 조건을 바탕으로 등록 자료를 만들고, 현재 환경에서 제공하는 브라우저 또는 공식 연결 도구로 등록한다. 사용자 계정·상품 ID·가격·보관함 주소를 고정값으로 추정하지 않는다.

## 작업에 맞는 문서

- 계정·가격·공개 범위 확인과 파일 준비: [공통 절차와 기록 도구](references/workflow.md).
- 리틀리: [리틀리 등록](references/littly.md).
- 포스타입: [포스타입 등록](references/postype.md).
- 원스토어: [원스토어 등록](references/onestore.md).

해당 플랫폼 문서만 추가로 읽는다. 제작 스킬이 만든 bundle-manifest.json을 받거나 같은 규격으로 기존 파일의 해시·미리보기·지원 운영체제를 확인한다. 제작 스킬이 설치되지 않았어도 완성된 manifest와 파일이 있으면 등록을 준비할 수 있다.

## 중요한 구분

- 가격과 공개 범위는 플랫폼별로 저장한다. 무료 구독자 공개와 유료 멤버십 공개, 포스트 구매자 공개는 서로 다르다.
- 준비·작성 요청은 자료와 초안까지다. 사용자가 대상과 조건을 지정해 업로드·발행을 요청했다면 그 승인 범위에서 수행하고 같은 승인을 반복해서 요구하지 않는다. 실제 도구가 요구하는 승인 규칙은 지킨다.
- 설치 파일 구조 검사, APK 서명 확인, 앱 실행, 카카오톡 내부 적용은 별개다. 판매 설명에 검증되지 않은 호환성을 보증하지 않는다.
- 원스토어 심사 접수는 판매 시작과 다르다. 실제 상태를 읽고 그대로 보고한다.
- 한 플랫폼이 막혀도 다른 플랫폼에서 승인된 작업을 진행할 수 있다. 이미 성공한 플랫폼은 재발행하지 않는다.

## 실제 등록과 중복 방지

1. 로그인된 계정과 실제 상품 목록을 읽고 이름·패키지·기존 ID로 중복을 확인한다. 과거 로컬 기록만으로 현재 등록 상태를 확정하지 않는다.
2. 상품별 자료를 준비하고 파일·가격·공개 범위를 검사한다. 공개 원고에는 제작 과정이나 기술 검증 보고를 길게 넣지 않는다.
3. 원격 초안을 만들면 ID와 URL을 즉시 bind로 기록한다. 생성 응답이 불명확하면 먼저 목록에서 생성 여부를 확인한다.
4. 저장된 파일·가격·공개 범위와 사용자의 승인을 확인한 뒤 attempt를 기록하고 최종 등록·발행·심사 요청 버튼을 한 번 누른다.
5. 결과 화면과 실제 상품을 확인해 confirm으로 기록한다. 응답이 끊기면 reconcile로 기존 ID의 상태를 확인한다. 상태를 확인하기 전 최종 버튼을 다시 누르지 않는다.

제공 스크립트는 파일 준비와 상태 기록만 수행한다. 웹사이트 업로드는 에이전트가 사용 가능한 브라우저 도구로 수행한다. 로그인·추가 인증·화면 변경·연결 오류로 진행할 수 없다면 준비한 자료와 정확한 재개 지점을 보존하고 실제 미완료 상태를 보고한다.

## 실행과 완료 보고

외부 터미널이나 브라우저 창을 강제로 띄우거나 사용자의 입력 초점을 빼앗지 않는다. 검증용 브라우저는 가능한 경우 headless를 사용한다. 비밀번호·쿠키·API 키·서명키를 작업 문서나 공개 저장소에 저장하지 않는다.

최종 보고에는 플랫폼별 실제 URL·상품 ID·가격·공개 범위·현재 상태를 적는다. 결제를 실행하지 않았다면 구매 화면 확인과 결제 후 전달 확인을 구분한다. 원스토어에는 심사 접수 여부를 명시한다.
